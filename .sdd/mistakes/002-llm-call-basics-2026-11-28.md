# 002 タスク 3.6: 範囲を決めない静的検査が膨らんだ（2026-11-28 記録）

成果物の合否は [check.md](../../specs/002-llm-call-basics/pdca/check.md) にある。ここでは、進め方で起きた 1 件と、付随する 1 件を記録する。

## 事故 1: 「漏らさない」の静的検査が、レビューのたびに回避された

- **What happened**: `scripts/hello.ts` が prompt や `cause` を標準エラーに出さないこと（5.7）を、ファイルを読む文字列の検査で確かめていた。`/sdd-ship` の Codex が「`explain()` の中で `String(error.cause)` を返しても 8 件が GREEN」と指摘し、再現した。直すたびに Codex が新しい回避を示した（テンプレートの `}`、正規表現、`join("")`、`console?.error`、`node:fs` + `Symbol.hasInstance`、catch の中の `const explain = unsafeExplain` ほか）。3 回目で構文木（`typescript/sync`）に切り替え、6 回目の時点で約 1,200 行、82 件になった。
- **Root cause**:
  1. 検査が**何を防ぐのか**（保守者が直す途中の現実的な回帰か、`hello.ts` を敵対的に書き換えるコードか）を、spec・plan・tasks のどこにも書いていなかった。敵対的なレビューは、範囲が書かれていなければ常に後者まで進む。
  2. 「出力に含まれない」という**振る舞い**の要求を、「ソースに書かれていない」という**構文**の性質で近似した。構文の閉じた集合は、言語の表現力の分だけ回避が見つかる。
  3. `hello.ts` は `server-only` と Ollama に依存し、テストから import できない。振る舞いで確かめる継ぎ目（`explain()` を `src/` の純粋関数にする）を plan の段階で用意しなかった。
- **Impact**: タスク 3.6 のテストは想定の数倍（約 980 行、72 件）になった。5・6 回目で足した import・宣言の規則は、解説の「プロバイダを変える方法」（import とモデル生成の 1 行を替える）と衝突し、ユーザーの判断で外した（作業の手戻り）。検査は beta の公開 API（`typescript/sync`）に依存する。CI の ubuntu で動くことは PR #10 で確かめられたが、版を上げると壊れうる。
- **Prevention**:
  - 「〜を漏らさない」「〜を出力しない」の要件には、plan に**検査の脅威モデルを 1 行**書く（例: 「対象は保守者の現実的な回帰。敵対的な書き換えは対象外」）。レビューの依頼文にも同じ行を渡す。
  - 振る舞いの要件は、まず振る舞いで確かめる。import できないスクリプトの出力を確かめるときは、整形の関数を `src/` に出し、偽の入力で出力を調べる継ぎ目を plan に入れる。構文の検査は、その継ぎ目がない場合の補助にする。
  - 敵対的レビューで**同じ種類の指摘が 2 回続いたら**（回避が見つかり続けたら）、3 回目を回す前に範囲をユーザーに確かめる。今回は 6 回目のあとで範囲を決め、決めたあとは 2 回で収束した。
  - 静的検査の PROVE には、**通るべき対照**（正当な改名、解説どおりの書き換え）を必ず入れる。今回は対照があったので、5・6 回目の規則が解説と衝突していることに気づけた。

## 事故 2: 差し戻し後の再実装が、状態の上では「出荷済み」に見えた

- **What happened**: `/sdd-ship` は REQUEST_CHANGES（MEDIUM 1 件）だった。3.6 の再実装は作業ツリーにあり、未コミットだった。それでも `sdd-autopilot-state.sh next` は `next: pr` を返した。そのまま push していたら、修正が PR に入らなかった。
- **Root cause**: 状態スクリプトは、未チェックのタスク数と wave の出荷記録で次の段階を決める。ship の判定（REQUEST_CHANGES）と、そのあとの再実装の有無は見ていない。
- **Impact**: pr 段の開始時に作業ツリーを確かめて気づいた。ユーザーの承認を得て 2 コミットにしてから push したため、実害はない。
- **Prevention**:
  - pr 段の最初に `git status --short` を見て、追跡ファイルの変更があれば止まる（今回はこれで防げた）。
  - 状態スクリプトの `next` が、作業ツリーに変更があるときや、最新の ship レビューが REQUEST_CHANGES のときに警告を出すようにする候補。
