# 001 実装中の事故と予防策（2026-11-27 記録）

作業結果の合否は [check.md](../../specs/001-dev-environment-and-gates/pdca/check.md) にある。ここでは、作業の進め方で起きた 2 件の事故を記録する。どちらも成果物の合否は変えなかったが、作業の証拠を損ねた。

## 事故 1: 復元の `cp` が外部の変更を上書きした

- **What happened**: `sandbox.ts`（タスク 2.1）と `check-commit-msg.mjs`（タスク 6.2）の PROVE で、壊したファイルを `cp` でバックアップから戻した。戻す前に、システムが「直前に読んだあとにディスク上で変わった」と通知していた。`cp` はその変更を上書きした。
- **Root cause**: 復元に `cp` を使い、戻す前に現在の内容を確かめなかった。通知を読んでから上書きした。
- **Impact**: 外部の変更の中身は確認できなくなった。`check-commit-msg.mjs` は、復元後に壊す前のコピーと一致したが、その変更が何だったかは分からない。作業の証拠として、この部分は再現できない。
- **Prevention**:
  - 復元は Edit で行い、`diff` で壊す前のコピーと一致を確かめる（以後の全タスクで実施）。
  - システムが「ファイルが外部で変わった」と通知したら、上書きする前に `diff` で差分を読み、ユーザーに確認する。
  - 作業中のファイルを `cp` で戻さない（`cp` は確認なしに上書きする）。

## 事故 2: 拒否された Edit のあとに、中途半端な状態が残った

- **What happened**: タスク 7.4 で、自動モードの判定が Edit を 2 回拒否した。1 回は `piped: false`、もう 1 回は `--redact` の削除。その後の復元の Edit が、部分的に適用された前の編集が残した文字列に一致し、Biome のフラグを `lefthook.yml` に 2 回入れた。`verify` が exit 1 になって気づいた。
- **Root cause**: 拒否のたびに、ファイルが期待した状態かを確かめず、次の Edit を重ねた。
- **Impact**: 検査の失敗として見つかったため、コミット前に直せた。ただし、フックの構成が一時的に壊れた状態で PROVE の結果を読んでいた。
- **Prevention**:
  - Edit が拒否されたら、次の編集の前に `diff` で壊す前のコピーと比べる（do.md の教訓と同じ）。
  - 1 つの PROVE グループの最後ではなく、Edit ごとに確かめる。
  - `verify` が予期せず落ちたら、まず作業の差分を見て、テストの失敗より前に状態を確かめる。

## 補足: 手元でしか再現しない問題の扱い

- 入れ子の Vitest の ANSI 色の問題（タスク 6.1）は、こちらの環境で再現せず、開発者の端末で計測してもらった。`NO_COLOR=1` と `FORCE_TTY=false` で 0 件になったが、機械ごとに違う理由は未特定。
- 予防: 手元でだけ再現する失敗は、再現しない環境の緑を修正の証拠にしない。計測を相手に頼むときは、変数を 1 つずつ外す手順を先に書いて渡す。
